# Обновление поиска и анти-повторов v3.2

## Исправление зависания v3.1

v3.1 требовала полного индексирования перед первым ответом. На `count=444972`
это превращалось в долгие ожидания и просьбы повторить команду. В v3.2 эта схема
убрана: свежий результат возвращается из уже просмотренного, а новые страницы
читаются постепенно. Это компромисс: глобально лучший арт непрочитанной выдачи
не гарантируется, но её дальнейшая глубина не обрезана.

- За вызов догружаем до 6 страниц, если новых подходящих кандидатов мало.
- Общего потолка в 6 страниц нет. Индекс и курсор находятся в постоянной папке
  DATA_DIR/search_cache и переживают рестарт/вытеснение из RAM.
- До 4 открытых индексов, до 3 HTTP-запросов одновременно на источник.
- Бюджет поиска 20 секунд, рабочий максимум 30. Старое env=120 будет ограничено 30.
- Новые проиндексированные кандидаты не теряются при сбое последующей страницы.
  Ни ошибка, ни исчерпание никогда не разрешают повтор. 401/403/429 явные.
- Пустая страница с count>0 — допустимый ответ API, не обязательно повреждённый JSON.
  count используется как ориентир. Повторяющиеся/преждевременно заканчивающиеся
  страницы логируются отдельно и не подменяются заявлением «прочитано всё».
- Ограничения сервиса не обходятся. При остановке доступной пагинации сузь теги.
- Контент-фильтры сохранены. Большой count не равен числу артов, которые пройдут фильтры.
- Полный старый снимок v3.1 был временным и не переносится; история shown.sqlite3 сохраняется.

Частичный индекс может содержать старые метаданные; он не является актуальным
полным снимком сайта. Для переиндексирования останови бот и удали только search_cache.
Готовые обходы после 10 минут могут обновляться, сохраняя известные кандидаты.
Изменение файла контент-политики создаёт другой ключ индекса. Индексы занимают
место на диске: при необходимости очищай search_cache, но НИКОГДА не историю.

## Строгая история

`shown.sqlite3` — история в области Discord-канала. Люди, запросы, исключающие
теги и booru-источники в одном канале делят этот журнал. Другой канал независим.
Discord-ветка считается отдельным каналом.

Нет вытеснения после 500 показов/запросов. Резерв записывается в SQLite до
скачивания; подтверждённая отправка фиксируется отдельной короткой транзакцией.
Проверяются MD5 API, ID поста и MD5/SHA256 фактического файла. Это не perceptual
hash: другого поста с перекодировкой/кропом эти проверки могут не распознать.
Telegram-альбомы проверяются по ID альбома и по байтам каждого вложения; при
совпадении любого вложения весь кандидат консервативно пропускается.

Если доставка была начата, но подтверждение потерялось (сеть/5xx/отмена/крах),
резерв **не снимается автоматически**. Это намеренный компромисс: возможен
пропуск не доставленного арта, зато не повторяется потенциально доставленный.
Точно отвергнутые отправки (например 413) освобождают резерв. Битые/слишком
большие файлы временно исключаются на 5 минут, до 8 попыток за вызов, 180 секунд
на скачивание/отправку. Эти ограничения не обрезают индекс поиска.

Неопределённые резервы вручную не удалять без проверки сообщений Discord и
остановленного бота. Автоматического «сброса ради нового арта» нет.

## Старая история

При первом запуске автоматически импортируется `recent_shown.json` из DATA_DIR.
В старом JSON нет Discord-каналов, поэтому сохранённые ID консервативно блокируются
во **всех** каналах. Маркер миграции хранится в SQLite; JSON не перезаписывается.
Ошибки чтения/повреждённая история останавливают работу, а не обнуляют защиту.

Вытесненные старой версией записи (старше 500 показов/запросов), незафиксированные
перед аварией показы и удалённый JSON восстановить из этого файла невозможно.
Новая версия не может гарантировать запрет исторических повторов, которых в
сохранённой истории уже нет. При потере новой SQLite-базы защита тоже потеряна.

## Порядок обновления

1. Остановить бот. Сделать резервную копию `recent_shown.json`, `.env` и DATA_DIR.
   Если уже есть `shown.sqlite3`, сохранять её после остановки вместе с WAL/SHM,
   если они присутствуют; не копировать живую SQLite-базу произвольным способом.
2. Применить патч/заменить исходники, включая **новый `search_index.py`**.
   Секреты, файлы сессий и рабочую историю не заменять файлами из архива исходников.
3. Задать постоянный, доступный для записи DATA_DIR с достаточным местом на диске.
   Для Docker нужен volume. Не включать историю в git или Docker-образ.
4. Установить прежние зависимости и проверить локально:

   ```bash
   pip install -r requirements.txt
   python test_bot.py
   python -m unittest -v test_antirepeat
   ```

5. Запустить бот. Убедиться, что импорт старой истории прошёл без ошибок.
6. На тестовом канале проверить:
   - одинаковый запрос несколько раз → разные ID;
   - перекрывающиеся теги → уже показанный файл не возвращается;
   - параллельные команды → не отправляют одинаковый арт;
   - рестарт → не сбрасывает историю;
   - полный обход тестового тега с >600 доступными постами;
   - временный сбой/429 → сообщение об ошибке, без старого результата;
   - исчерпание → сообщение, без повторов.
7. Проверить CPU/RAM/диск и время ответа на выбранном хостинге, затем обновлять
   рабочую ветку/перезапускать production. GitHub и хостинг этим патчем не обновлены.

## Локальная проверка

127 базовых проверок + 55 регрессионных теста. Включают: быстрый первый ответ
при count=444972 после одной страницы, постепенное прохождение 650 уникальных
результатов без повторов, доступ к посту 3199 при отсутствии подходящего в первых
600, сохранение курсора после рестарта и простоя, пустая страница с положительным
count, недооценённый count, таймаут/сбой поздней страницы с сохранением новых
результатов, атомарные резервы, неопределённая доставка и долговечность истории.
Диагностический полный обход и SQL-ранжирование проверяются отдельно.

Тесты моделируют API, не доказывают скорость/доступность реального Gelbooru.
На хостинге нужны проверка версии v3.2.0, времени ответа и Console при ошибках.
Новые строки логов показывают источник, страницу, next_page, fetched, total_hint
и причину ошибки/остановки. Токены и значения ключей в них не выводятся.

Для `/tg` глубина чтения истории всё ещё 200 сообщений. Строгий запрет повторов
и устойчивый peer-based ID применяются, но полный архив Telegram не импортируется.
